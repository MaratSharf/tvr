# Рекомендации: функция «Режим обучения» (эталонные изображения)

> Документ — только план. Код не изменён.

**Цель:** при включённом режиме обучения захваченные изображения сохраняются в
отдельную папку и в дальнейшем используются как эталоны для проверки.

---

## 1. Сначала определитесь, что именно является эталоном

В текущем пайплайне (`image_processor.py`) решение принимается по **геометрии**:
контур → `min(w, h)` → `px_per_mm` → диапазон `[min_width_mm, max_width_mm]`.
«Использовать кадры как эталоны» может значить три разные вещи:

| Смысл эталона | Что хранится | Как проверяется | Сложность |
|---|---|---|---|
| **А. Визуальный шаблон** | сам PNG + нормализованный ROI | pHash / `matchTemplate` / профиль сечения | низкая |
| **Б. Числовой эталон (SPC)** | метрика: ширина, площадь, положение bbox | `mean ± k·σ` по базе вместо жёстких min/max | низкая |
| **В. Размеченный датасет под ML** | PNG + метка OK/NOK | обучение модели (ONNX) | высокая |

Рекомендация: **А + Б как гибрид**, В — отдельным этапом.

Гибрид даёт два независимых контроля:
- «кадр похож на эталон» — ловит смещение детали, подмену, загрязнение оптики;
- «метрика внутри допуска, вычисленного из эталонов» — ловит реальный брак по шву.

**Новые зависимости не нужны** — критично, так как `OFFLINE_INSTALL.md` фиксирует
версии под Windows 7 + Python 3.8, и любое новое колесо требует пересборки `wheels/`.

```json
"training": {
    "enabled": false,
    "mode": "capture",
    "folder": "C:\\proj\\python\\tvrus\\data\\etalon",
    "group_by_product": true,
    "max_samples_per_group": 20,
    "match": {
        "method": "phash",
        "hamming_max": 8,
        "profile_tolerance_pct": 15.0
    },
    "limits": {
        "sigma_k": 3.0,
        "min_samples": 10
    }
}
```

Обязательные дополнения в `main.validate_config()`:

- `training.mode` ∈ `{capture, verify}`;
- если `training.enabled` и `mode == 'verify'` — в базе должно быть
  ≥ `min_samples` эталонов, иначе **отказ запуска**, а не тихий возврат
  к старым `min/max_width_mm`.

> Обоснование: в `main.py` уже реализован аналогичный принцип — «отказ связи —
> это авария, а не повод для тихого перехода в simulation». Здесь та же логика:
> молча подменить эталонный допуск на ручной значит выпустить брак как OK.

## 3. Структура базы эталонов

```
data/etalon/
├── ProductID_01/
│   ├── ET_20261023_103015_4.25mm.png
│   ├── ET_20261023_103015_4.25mm.json      # sidecar-метаданные
│   └── index.json                          # хеши + метрики, кэш при старте
├── ProductID_02/
└── ...
```

Правила:

- **Sidecar на каждый кадр вместо одного большого файла** — переживает ручное
  добавление/удаление кадров, не требует миграции базы.
- **`index.json`** — массив записей `{file, phash, width_px, width_mm, area, bbox,
  roi, exposure, gain, label, defect, ts, note}`. Грузится один раз при старте и
  держится в памяти как `numpy`-матрица хешей: сравнение с 200 эталонами — одна
  векторизованная операция, укладывается в `limits.cycle_time_s = 0.8`.
- **`ProductID`** — группировка уже есть в структуре проекта
  (`Медиа с камер тек процесса\ProductID_01…99`), так что ложится естественно.
- **Отдельная папка от `data/results`** — обязательно: `results` это журнал
  с авточисткой (`storage.max_files` / `storage.max_age_days`), эталоны
  авточисткой удалять **нельзя**. Не добавлять `training.folder`
  в список папок в `run_storage_cleanup()`.
- **Запись только атомарно** — по образцу `gui.save_config_atomic()` и
  `ROIManager.save_to_config()`: `tempfile.mkstemp()` + `os.replace()`.
- **Дедупликация** — перед записью сверить pHash с `index.json`; при совпадении
  предупредить оператора, не плодить копии.

Содержимое sidecar-файла:

```json
{
    "file": "ET_20261023_103015_4.25mm.png",
    "product_id": "ProductID_01",
    "label": "ok",
    "defect": "",
    "note": "эталон OK, партия 1",
    "ts": "2026-10-23T10:30:15",
    "roi": [295, 112, 613, 760],
    "px_per_mm": 50.0,
    "threshold": 120,
    "exposure": 10000,
    "gain": 1.0,
    "width_px": 212,
    "width_mm": 4.24,
    "area": 161240,
    "bbox": [301, 118, 214, 748],
    "phash": "c3f1a0d7e2b84519"
}
```

## 4. Новые модули (по одномуResponsibility, как остальной код)

### `etalon_store.py`

```python
class EtalonStore:
    def __init__(self, config, roi): ...
    def load_index(self) -> None: ...        # numpy-кэш хешей и метрик
    def add(self, image, metrics, product_id=None, note='') -> str: ...
    def groups(self) -> list[str]: ...
    def stats(self, group) -> dict: ...      # mean, std, min, max по width_mm
    def limits(self, group) -> tuple[float, float]: ...   # mean ± k*sigma
    def mark_stale(self, reason: str) -> None: ...
```

### `etalon_matcher.py`

```python
class EtalonMatcher:
    def phash(self, gray_roi) -> int: ...    # cv2.resize → cv2.dct → порог по медиане
    def hamming(self, a: int, b: int) -> int: ...
    def find(self, gray_roi) -> tuple[dict | None, int]: ...  # лучший эталон + дистанция
    def profile(self, gray_roi) -> np.ndarray: ...  # N поперечных срезов ширины/яркости
```

`cv2.dct`, `cv2.matchTemplate`, `cv2.resize` — всё присутствует
в `opencv-python==4.8.1.78`, новых пакетов не требуется. SSIM, если понадобится,
лучше написать на `numpy` в ~15 строк, чем тянуть `scikit-image`.

## 5. Точки врезки в существующий цикл

Не переписывать `SeamProcessor.process()`. Добавить слой-обёртку:

```python
class ReferenceProcessor:
    """Обёртка: матчинг с эталоном + допуск из базы, поверх SeamProcessor."""

    def process(self, image):
        # 1. тот же ROI/GRAY/CLAHE, что и в SeamProcessor (вынести в общий хелпер)
        # 2. etalon_matcher.find(...) -> (эталон, дистанция)
        #    дистанция > hamming_max  => NOK "не похож на эталон" (смещение/подмена)
        # 3. ok, width, msg, bbox = self.base.process(image)   # геометрия как сейчас
        # 4. lo, hi = store.limits(group) => переопределить ok по числовому эталону
```

В `main.py` — минимально инвазивно, в трёх местах:

- `run_modbus_mode` / `run_profinet_mode`: сразу после `processor.process(image)`
  вставить ветку

  ```python
  if training_capture:      # режим обучения: кадр в базу, результат НЕ шлём в ПЛК
      store.save(image, (ok, width, msg, bbox), product_id)
      reporter.status(f"Эталон сохранён: {width:.2f}mm")
      continue              # без send_result, без OK/NOK-ламп
  ```

- **Ключевое правило безопасности:** в `training.mode == 'capture'` запрещены
  `comm.send_result()` и `comm.set_conveyor()` — иначе обучающие кадры будут
  ронять лампы и толкатель брака на реальной линии. Проще и надёжнее вынести
  обучение в отдельный `run_training_mode(...)` и не запускать его
  через `create_communicator(...)`.

- `finally`-блок с `outputs_reset_checked(comm)` оставить как есть — он уже
  гарантирует сброс DO при падении.

## 6. GUI — что добавить в `gui.py`

- Чекбокс **«Режим обучения»** в тулбаре + переключатель `Захват / Проверка`.
- Кнопка **«💾 В эталон»** — сохраняет *последний* кадр (`self.last_raw`,
  уже передаётся через `GuiReporter.result(..., raw=image)`),
  с обязательным подтверждением оператора (`messagebox.askyesno`).
  Без подтверждения в базу неизбежно попадёт брак.
- Поле **«ProductID»** (комбобокс из `store.groups()`).
- Поле **«Комментарий»** — причина эталона («эталон OK», «эталон NOK: пористость`).
- Панель **«База эталонов»**: число образцов, `mean ± σ`, текущий автодопуск,
  кнопка пересчёта лимитов.
- Счётчики в `stats_label` — отдельно `OK/NOK` (проверка) и `Сохранено эталонов`
  (обучение), чтобы не смешивать.
- Все операции — **через `ui_queue`**, как сейчас: рабочий поток не трогает
  Tkinter. Запись эталона из worker-потока — только по событию в очередь.

## 7. Разметка «эталон брака»

Заложить в sidecar `"label": "ok" | "ng" | "unknown"` и `"defect": "..."`
уже сейчас. Даже без ML это:

- позволяет исключить NG-образцы из расчёта `mean ± σ` (иначе допуск
  «размоется» браком);
- даёт готовый датасет, если позже решите этап В.

## 8. Калибровка и воспроизводимость

Эталон имеет смысл только при фиксированных условиях съёмки:

- при добавлении эталона в sidecar писать **`exposure`, `gain`, `roi`,
  `px_per_mm`, `threshold`** — и при проверке сверять с текущим `config.json`;
  при расхождении предупреждать, что эталоны невалидны;
- при изменении ROI (`ROIEditor._save_roi`) — **помечать базу как устаревшую**
  (`store.mark_stale()`), так как ROI входит в нормализацию кадра и старые хеши
  теряют смысл. Альтернатива — хранить ROI в sidecar и пересчитывать хеш на лету;
- то же при калибровке `px_per_mm` в «Настройках»: пересчитать метрики эталонов
  (`width_mm` — производная от `width_px`).

## 10. Порядок реализации (каждый этап самодостаточен)

1. Секция `training` в `config.json` + `validate_config()` + `EtalonStore`
   (запись/индекс) — **без изменения цикла**, только сохранение кадров в новую папку.
2. `run_training_mode()` + кнопка/чекбокс в GUI + запрет `send_result`
   в capture-режиме.
3. `EtalonMatcher` (pHash) + `ReferenceProcessor`: «похож / не похож».
4. Автодопуск `mean ± k·σ` поверх геометрии, UI-панель статистики.
5. Разметка OK/NG-эталонов + группировка по ProductID.
6. (опционально) экспорт размеченного датасета под ONNX.

## 11. Чего делать не стоит

- Не хранить эталоны в `data/images/foto/NG` — туда пишет камера,
  и `camera._read_latest_from_folder()` начнёт читать эталоны как новые кадры
  (фильтр идёт по `mtime`).
- Не применять к `training.folder` `cleanup_folder()` / `storage.*`.
- Не менять `SeamProcessor.process()` под обучение — только обёртка,
  иначе сломается отлаженный production-путь.
- Не тянуть `scikit-image`, `torch`, `opencv-contrib` из-за `wheels/` и Win7:
  если ML понадобится — `onnxruntime` отдельным wheel-набором и отдельной веткой.
- Не трогать `ml121_200rb_100/` (бэкап KUKA).
